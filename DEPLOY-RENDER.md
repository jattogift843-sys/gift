# Deploying to Render

The whole platform runs as **one Render Web Service** — it serves the API and
both frontend bundles. The database is **Supabase** (external); Render doesn't
host it.

`render.yaml` in the repo root is a Blueprint that pre-fills the build/start
commands, health check, and the list of environment variables.

---

## 1. Prerequisites

- The repo is on GitHub and pushed.
- A Supabase project with the schema applied (`npm run db:migrate` — already done).
- Your two Supabase connection strings ready:
  - **transaction pooler** — `postgresql://postgres.<ref>:<pw>@aws-0-<region>.pooler.supabase.com:6543/postgres?sslmode=require`
  - **session pooler** — same host, port **5432**

## 2. Create the service

1. Render dashboard → **New → Blueprint**.
2. Connect the GitHub repo (`jattogift843-sys/gift`). Render finds `render.yaml`.
3. **Apply**. Render prompts for every variable marked `sync: false` — paste:

   | Variable | Value |
   |---|---|
   | `DATABASE_URL` | transaction pooler string (`:6543`) |
   | `DIRECT_URL` | session pooler string (`:5432`) |
   | `ADMIN_EMAIL` / `ADMIN_PASSWORD` | your production admin login |
   | `MEMBER_EMAIL` / `MEMBER_PASSWORD` | a demo member, or reuse the seed defaults |
   | `SMTP_*` | leave blank unless you want real email — alerts log to the admin Email Log otherwise |

   `JWT_SECRET` is generated by Render. `NODE_ENV`, `TRUST_PROXY`, `PORT` are set for you.

4. First build takes ~2–3 min. When it's live, open the service URL — the landing
   page loads, `/app` and `/admin` work, and the admin/member accounts are seeded
   automatically on first boot.

## 3. Region

`render.yaml` pins **Frankfurt** to sit next to a `eu-central-1` Supabase project
— that's the difference between ~10 ms and ~1 s per query. If your Supabase
project is elsewhere, change `region:` in `render.yaml` to match
(`oregon`, `ohio`, `virginia`, `singapore`).

## 4. Schema changes later

`render.yaml` does **not** run migrations on deploy (Render's free plan has no
pre-deploy hook). After changing `src/db/schema.js`:

```bash
npm run db:generate      # locally — writes the SQL migration
git commit -am "db: …" && git push
npm run db:migrate       # locally, against DIRECT_URL — applies it to Supabase
```

Render redeploys the code; the schema was already updated by the line above.
(On a paid Render plan you can move `npm run db:migrate` into a pre-deploy command.)

## 5. Gotchas

- **Supabase free tier pauses the project after ~7 days idle** — the app then
  errors until you un-pause it in the Supabase dashboard.
- **Render free web services spin down after ~15 min idle** and cold-start
  (~30–60 s) on the next request. Upgrade the instance for always-on.
- Change `ADMIN_PASSWORD` / `MEMBER_PASSWORD` from any values used in development.

## 6. Splitting the frontends later (optional)

The repo already separates `frontend/site` and `frontend/app` into standalone
bundles. To host them as their own Render **Static Sites** instead of letting the
web service serve them:

1. New → Static Site → root directory `frontend/site` (and again for `frontend/app`).
   Publish directory: the folder itself; no build command.
2. In each bundle's `config.js`, set `apiBase` to the web service URL + `/api`,
   and the cross-bundle URL.
3. On the web service, set `CORS_ORIGINS` to the two static-site origins
   (comma-separated).

See each bundle's `DEPLOY.md`.
